# Moving to UChat — context

## Why this exists

- **29 Sep:** UChat was evaluated and not adopted ([../11-whatsapp-bot/context.md](../11-whatsapp-bot/context.md), "29 Sep"; [uchat-comparison.md](../11-whatsapp-bot/uchat-comparison.md)).
- **18 Oct:** the owner confirmed we stay on Chatwoot, *"because its already built and migration on uchat will mean we will create it from the start again"*.
- **3 Nov:** the owner, after a week in which Meta deleted our test account and the bot moved to a new test number: *"ok so we need to prep for migration to uchat just in case"*.
  - The decision to stay is unchanged. This folder makes a move quick and safe if it is ever needed.
  - It answers the owner's own 18 Oct worry: in this route, nothing about the bot is built again.

## Decisions

**UChat replaces Chatwoot; the bot stays in n8n.**
- It keeps the before-sending checks, the replay tests and the memory, the things that stopped this autumn's "fix one, break another".
- It is the shorter road: 13-19 days against 21-34.
- Rejected: the bot rebuilt as a UChat AI agent. UChat's AI step gives no check before a reply goes out, and the Hebrew tuning would start again on another wrapper.

**Build beside the live bot, as a copy, and cut over in one sitting.**
- This is how the sandbox was built on 26 Oct, and the fingerprint of production stayed unchanged.
- Rejected: changing the live workflow step by step. The live bot would break the day the first step lands, because the number cannot be on both platforms' bots at once.

**The tool server's three WhatsApp sends go behind one switch.**
- The cutover and the rollback then change a setting, not code.

**Chatwoot keeps running after the move.**
- It is the archive, the rollback target, and possibly the Voice inbox.
- Turning it off would save nothing: it shares the server with n8n.

**The menu becomes a UChat flow node that n8n sends.**
- This is the platform's own way to send buttons, the owner's 22 Sep rule of using the platform's feature rather than rebuilding it. Its quick replies come back as ordinary messages.

**The UChat version talks to UChat through a translator that speaks Chatwoot (3 Nov).**
- The bot copy keeps live's Chatwoot calls exactly, with only the host and token changed. A separate workflow does each call through UChat's API and answers in Chatwoot's shape.
- So the copy is the live bot regenerated by a script, and a change on live reaches it by re-running that script.
- Rejected: rewriting the bot's ten Chatwoot steps into UChat calls. Each would drift from live with every change to those steps' wording.

**The UChat version uses the live tools, behind a test-phone allowlist (3 Nov).**
- It is a version of the chatbot, not a sandbox. Its tickets, balances and links are the real ones, like a test on the live WhatsApp bot (Bar Kochba 23, as Assaf Clix).
- The allowlist keeps anyone else who reaches the web chat from opening a real ticket.
- Rejected: the sandbox function. Its deploy is v8 of 29 Oct, 10:29 UTC, so it predates live's `add_request_detail` (29 Oct evening) and the reporter's name (v138, 30 Oct). The copy would not behave like the bot.

**The message is read back from UChat, not taken from the External Request (3 Nov).**
- UChat's "Last Text Input" and "Last Button Title" outlive the message that set them, so a typed message after a tap would carry the old title.
- UChat's own log gives the newest message and its id. It is the same id the burst check later compares.

**A dry run on the free workspace comes before any build.**
- The payload, the notes question and Hebrew right-to-left are the three things that can change the plan.
- All three are answerable with the web chat widget, without a WhatsApp number and without money.

**UChat is set up like our Chatwoot, name for name (3 Nov, owner: *"ok just make uchat like the settings we have on the chatwoot"*).**
- The four departments are UChat agent groups with Chatwoot's team names, the eight labels are UChat labels with Chatwoot's names, and the owner sits in `service`, as in Chatwoot.
- Same names, so a hand-over reads the same in either inbox, and the mapping is one line (`UCHAT_GROUPS`).

**The groups give a chat to Least Assigned (3 Nov).**
- UChat has no "assign to the group and nobody": its methods are Random, Least Assigned and Round Robin.
- Least Assigned spreads chats the most evenly once real staff are in. With one member it makes no difference.
- Assignment does not pause the bot (proven 3 Nov), so the behaviour after a hand-over is Chatwoot's.

**A label goes on twice, as a tag and as a UChat label (3 Nov).**
- The tag is what the copies read back: UChat's contact record (`BotUser`) carries tags, not labels, and the off switch reads `bot-off` from it.
- The label is what staff see and filter on in Live Chat, as they did in Chatwoot.
- Rejected: labels only. The switch would stop seeing `bot-off`, and reading labels too would cost one more UChat call on every message.

## Constraints

- **UChat provides no numbers.** Every number is registered with Meta under a Meta business account ([uchat-trial.md](../11-whatsapp-bot/uchat-trial.md)).
- **UChat's guided connection is its own Meta app.** WhatsApp Cloud uses a Facebook login, Meta's embedded signup.
  - Meta delivers each message to every app subscribed to the account. So whatever answers the number today keeps answering until it is switched off: two bots on one number.
  - Seen on 2 Nov: respond.io's app on the ASTDX account, where both would get the same messages.
- **The API cannot make flows, AI agents or integrations.** The Webhook integration and the web widget are switched on in the dashboard by a person (verified on the spec, 257 paths on 3 Nov).
- **The API has no internal-note call.** Chatwoot's private note, which pages a department today, has no direct twin. Searched the spec for "note": only closing notes, which are reasons chosen when a chat is closed.
- **A staff reply pauses the bot for 30 minutes,** which staff can extend (UChat's Live Chat docs). `pause-bot` takes any number of minutes.
- **UChat's External Request step times out after 15 seconds,** plus 10 per paid add-on. Our bot takes 20-40 seconds, so it never answers inside UChat's request. It acknowledges at once and replies through `send-content`, as the bot.
- **UChat's API sits behind Cloudflare,** which refuses Python's default user agent ("Error 1010: browser_signature_banned", a 403 that looks like a bad key). curl's passes. `scripts/uchat_api.py` sends it.
- **Two keys, two abilities (3 Nov).** Groups, labels, members and business hours need "Manage Team"; everything the bot does needs "Manage Flow".
  - `Uchat_api_key` ("homies-n8n", Manage Flow) is the bot's, in the translator's credential.
  - `UCHAT_API_KEY_TEAM` ("homies-team-setup", Manage Team only) is for setting the workspace up.
  - UChat shows a new key once. Without "Manage Team" the answer is 403 "Manage Team Permission Required".
- **No API call invites a member.** People are added in Workspace Settings → Members, and each invite emails that person.
- **Past messages cannot be imported.** The API creates contacts, not their history.
- **On the free plan, nothing in UChat can call another system.**
  - External Request, Integrations (the Webhook integration), Notification and AI Actions are all Pro.
  - The builder refuses them with "Upgrade to Pro account to use this feature" (3 Nov).
  - WhatsApp Cloud is Pro as well. So the UChat version needs the Business plan before it can answer anyone.

## Known failure modes

- **Two replies to every message at the cutover,** if the old path is not switched off in the same sitting. The cutover's step 3 exists for this.
- **The payload changes under us.** UChat does not publish it, so a silent change would break `Sort`. The copy's `Sort` must fail loudly on a shape it does not know, the lesson of 17 Sep's silent Send.
- **A reply outside the 24-hour window fails.** It is the same Meta rule as today: `send_payment_link` already falls back to `payment_link_he`, and the "done" message is a template anyway.
- **The tool server's sends must go as the bot, not as staff.** Today it posts with Chatwoot's bot token so the bot's workflow neither answers the message nor takes it for a staff takeover. In UChat a message sent as an agent (`send_as_agent: 1`) would start the staff pause. **Seen 3 Nov:** `send-text` is logged as an agent's message and paused the bot, so every reply goes through `send-content` with `send_as_agent: 0`.
- **Photos stop reaching tickets** if UChat's media host is not added to `MEDIA_HOSTS`.
- **The typing dots disappear** if UChat stops passing Meta's message id (`mid` in `chat-messages`; it does since 3 Nov), or if the system-user token loses the UChat number. The replies are not affected.

- **The UChat version answers nobody if UChat's contact id is not `<flow>u<number>`.** The translator rebuilds the contact id from the bot's flow id (`UCHAT_FLOW_NS`) and Chatwoot's numeric conversation id. The hand-over's `Report back` types the conversation id as a number, so a text id cannot pass through.
- **A caller without the secret still makes the way in read UChat twice** before Sort refuses them and answers nothing. They learn nothing; it costs two reads.
- **WhatsApp refuses a menu whose buttons share an id** ("#131009 Duplicate button id", 3 Nov). UChat makes a button's id from the step it runs, so each button has its own step. UChat's web chat accepts the same message, so only WhatsApp shows the fault.
- **A message in UChat's log is not a delivered one.** A sent message carries WhatsApp's id (`mid`, `wamid…`). Without one, WhatsApp refused it, and the reason is in UChat's error log (`GET /flow/error-logs/data`).

## Open questions

Each one is settled by the dry run (feature.md, step 1) or by the UChat version's first message, unless it says otherwise.

- **Settled 3 Nov, on WhatsApp:** `chat-messages` returns the newest message first. A button tap arrives as a `postback` message whose content is the button's caption, quoting the menu's WhatsApp id (`reply_to_mid`); the way in reads it as the caption, as it assumed.

1. **What UChat's Webhook integration posts:**
   - its fields;
   - whether a photo comes as a link, and from which host;
   - whether Meta's message id is in it;
   - whether a signature or secret comes with it;
   - whether it still posts while the bot is paused. UChat's changelog adds a "live chat webhook" for paused chats.
2. **How a department is paged:** a ticket-list item, or a flow node with a staff notification. Which one staff actually see on the phone app decides.
   - **Partly settled 3 Nov:** a hand-over puts the chat in the department's group, and UChat gives it to one member (Least Assigned). What that member is notified with, on the phone app, is not yet seen.
3. **Hebrew right-to-left** in Live Chat and the mobile app.
   - **The web dashboard: settled 3 Nov.** With the owner's profile in Hebrew it reads Hebrew and turns right-to-left. Live Chat and the mobile app are not yet seen.
   - Hebrew is listed among UChat's interface languages, and a July 2022 post claims right-to-left.
   - Its mobile-app page lists no Hebrew, but that page is about four years old.
4. **Whether our Meta test number can be connected at all.**
   - It lives in the HOMIES app's test account. Embedded signup most likely does not offer it.
   - The deprecated manual screen (token, account id, number id) might take it, if UChat still runs that screen.
   - Settled only when a number is actually tried. Never on the live number while the bot runs on it.
5. **The billing currency, and the plan's limits on the free workspace.** The pricing page shows no currency (29 Sep). Settled from UChat's checkout page.
