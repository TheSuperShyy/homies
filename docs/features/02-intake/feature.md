# 02 — Intake

**Estimate:** 1.5d
**Depends on:** [01-identity](../01-identity/feature.md)
**Status:** not started

## Purpose

Turn what the caller said into a `requests` row a dispatcher can act on without
phoning them back. This is the product. Everything else in the demo exists to
make this survive contact with a real caller.

## Behaviour

Four slots to fill, only two of which are asked for directly.

| Slot | How it is obtained |
|---|---|
| `building`, `unit` | carried from identity — never re-asked |
| `description` | the caller's own words, lightly cleaned |
| `type` | inferred from the description, confirmed only when ambiguous |
| `urgency` | inferred; asked only when the description is neutral |

**Description is the caller's words.** The agent does not summarise into
categories. "יש נזילה מהתקרה בחדר האמבטיה, זה כבר יומיים" is a better
description than "plumbing issue." Dispatchers read these; a paraphrase loses
the two-days detail that decides scheduling.

**Type is inferred, not interrogated.** A leak is plumbing. Asking a caller to
choose from a menu is the phone-tree experience this system exists to replace.
Confirm only when genuinely ambiguous — "no hot water" could be plumbing or
electrical.

**Urgency is inferred from language, not asked.** "It is flooding" is high.
"Whenever someone is passing" is low. When nothing in the description signals
either way, default to `normal` and do not ask. The emergency branch lives in
[06-boundaries](../06-boundaries/feature.md).

**Read-back before writing.** One sentence, then the reference:

> "רשמתי: נזילה מהתקרה באמבטיה, הרצל 14 דירה 12. מספר הקריאה שלך: 1, 0, 0, 1."

**Spoken, only the tail is read out.** `open_request` returns
`255-1001-26`; the caller hears `1, 0, 0, 1`. The office code and the year are
constant across every reference in the system, so they add nothing but four
more chances to mishear on the one line that has to be written down correctly.
Lookup is unaffected — `get_request_status` matches on the tail already, which
is what makes [03-recall](../03-recall/feature.md) work, and the WhatsApp bot
accepts it in either form. The full reference is still what is stored and what
the dashboard shows.

If the read-back is corrected, the correction updates the row rather than
opening a second one.

## Interface

**`open_request`**

| Field | Type | Required | Notes |
|---|---|---|---|
| `resident_id` | uuid | no | null when identity did not match |
| `building` | string | yes | from identity |
| `unit` | string | no | from identity |
| `type` | string | yes | plumbing, electrical, cleaning, other |
| `description` | string | yes | caller's words |
| `urgency` | string | no | defaults to `normal` |
| `call_id` | string | yes | Vapi call id |

Returns:

```json
{ "reference": "255-1001-26", "request_id": "uuid" }
```

Partial calls take a different path entirely — see
[07-partial-ticket](../07-partial-ticket/feature.md).

## Data

Writes one `requests` row: `resident_id`, `building`, `unit`, `type`,
`description`, `urgency`, `status = 'open'`, `opened_via = 'voice'`.
`reference` is generated by the column default from `request_reference_seq`.
`interaction_id` is backfilled by the end-of-call webhook.

## Acceptance

1. Ten open-mic calls produce ten rows, each with a description a dispatcher can
   act on without calling back. Judged by the ops staff in Act 2, not by us.
2. Building and unit in the row match what the caller said, on all ten.
3. No call asks for building or apartment twice.
4. A correction during read-back updates the existing row; no duplicate is
   created.
5. The reference read aloud matches the reference in the Sheet.
6. Zero rows where the type is confidently wrong. A missing type is acceptable;
   an incorrect one is not.

## Out of scope

Complaints, payment links, app instructions and every other PRD §7 tool
(release 1) · attaching photos · scheduling or promising a visit time ·
duplicate detection against existing OXS requests · writing anything to OXS.
