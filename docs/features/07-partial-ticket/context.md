# 07 — Partial ticket — context

## Why this exists

Two reasons, and the second is the one that made it a feature.

**The demo reason.** An open mic where a call produces nothing is a hole in the
room's confidence that no amount of good tickets fills. Every call must leave a
mark.

**The real reason.** What happens today when a call is unintelligible is
voicemail, and voicemail nobody transcribes is indistinguishable from a lost
call. A row holding the building, a recording, and a flag is strictly better
than the current state of the world — which makes this the one feature that is
easiest to argue for in the room, because it is measured against nothing rather
than against a competent human.

## Decisions

**Save what exists rather than discarding the call.** The alternative — no row
on failure — optimises for a clean database at the cost of losing the resident.
A partial ticket costs a human a two-minute callback. A lost call costs a
relationship.

**Never guess to fill a gap.** A partial ticket's entire value is that the
filled fields can be trusted. One invented apartment number and a human has to
re-verify every field on every partial row, which makes all of them worthless.
Same rule as [05-messy-input](../05-messy-input/context.md), applied where the
temptation is strongest.

**Say it out loud on the call.** Saving silently and hanging up leaves the
resident believing nothing happened, so they call again — which doubles the
work rather than saving it.

**`needs_review` as a status, not a boolean flag.** It is a state in the
workflow: it belongs to someone, it is worked, it leaves the state. A separate
boolean would need reconciling with `status` on every query.

**The Sheet is the review queue.** Building a triage UI for a demo that already
mirrors to a spreadsheet is redundant. Ops staff filter spreadsheets natively.

**Partial tickets are excluded from recall.** Reading back "I have a record that
I could not hear you" converts a save into an embarrassment. See
[03-recall](../03-recall/context.md).

## Constraints

- `requests.type`, `description` and `building` are `not null` in
  [001_slice_schema.sql](../../../supabase/001_slice_schema.sql) lines 86–88.
  Blocking; migration 003 is not optional.
- `requests.status` has a four-value check constraint at line 93.
- `reference` is generated by the column default, so a partial ticket gets one
  automatically and consumes a sequence value like any other row.
- Vapi provides the recording URL in the end-of-call payload, which arrives
  *after* the row is written — so `audio_url` is backfilled, not written inline.

## Known failure modes

- **Triggering too eagerly,** giving up on calls a human would have recovered.
  The threshold is a judgment call that only rehearsal settles, and the softest
  number in this feature.
- **Triggering too late,** producing a wrong ticket instead of a partial one.
  This is the worse direction to err in.
- **Partial rows accumulating unworked.** No consequence in a demo; a real
  problem in production, where `needs_review` needs an owner and an SLA.
- **The recording backfill failing,** leaving a partial row with no audio — the
  one thing that makes it actionable. Worth checking explicitly in acceptance.
- **Ops staff reading partial tickets as the system failing** rather than the
  system catching. Framing, not engineering: present it as better than
  voicemail, out loud, before it appears.

## Open questions

- What exactly triggers it — two failed slots, a rolling confidence average, or
  elapsed time without progress? Two failed slots for now because it is simple
  and explainable. Rehearsal decides.
- Should the agent ask for a callback number before giving up? It is the single
  most useful field on a partial ticket, and on a web call there is no caller ID
  to fall back on. Argues for yes; costs a turn on a call that is already going
  badly.
- Does a partial ticket that a human completes stay `needs_review` in history,
  or move to `open`? Moves to `open`; the audit trail lives in the interaction.
  Revisit if ops want to count them.
