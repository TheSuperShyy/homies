# Homies — Voice Agent & Chatbot PRD (v1)

**Prepared by:** CLIX
**Date:** 30 July 2026
**Status:** Draft for approval
**Scope:** Phase 1 — Voice Agent + Chatbot for service requests, status checks, payment links, and complaint tickets.

---

## 1. Overview

A Hebrew-speaking AI **Voice Agent** (phone) and **Chatbot** (WhatsApp) that handle routine resident interactions for Homies, backed by an automation layer that reads from and reports into the OXS building-management system.

The agents do **not** replace staff. They handle repetitive requests, capture structured data, and escalate anything sensitive to a human.

The voice agent has **two purposes**:

| # | Purpose | Direction | Status |
|---|---|---|---|
| **1** | **Answering inquiries** — open request, status request, update payment info, complaint tickets | Inbound | ✅ **Current focus** |
| **2** | **Debt follow-up calls** — outbound collection outreach | Outbound | ⏸️ Later phase |

**In scope (v1):** inbound inquiries — open request · status request · update payment info in OXS · complaint tickets
**Out of scope (v1):** outbound debt follow-up campaigns, ManageChat migration, full Monday integration

## 2. Purpose 1 — Inbound Inquiries (current focus)

### 2.1 Open Request
Resident asks the agent to open a new service request.

- Agent identifies the resident (phone match, or asks for building/apartment)
- Captures: request type, description, building, unit, urgency
- Creates the request record and returns a reference the resident can quote later
- Confirms back to the resident in natural Hebrew

### 2.2 Status Request
Resident asks about an existing request.

- Agent identifies the resident and locates their open request(s)
- Reports current status in plain language ("the technician is scheduled for Sunday")
- If no request is found, offers to open one (falls through to 2.1)

### 2.3 Update Payment Info in OXS ⚠️ *destructive action — highest-risk flow*

Resident calls to **change their payment details** (e.g. new credit card, new bank account).

**Flow:**
```
1. Resident asks to change payment details
2. Bot DOCUMENTS the request (logged before anything is touched)
3. Bot VERIFIES the resident's identity          ← mandatory gate
4. Bot DELETES ("truncates") the existing payment info in OXS
5. Bot instructs the resident to log into the OXS app and enter new payment details
6. Bot confirms and closes the interaction
```

**Requirements:**
- **Verification is a hard gate.** No deletion occurs unless identity verification passes. Failed verification → no action taken, escalate to a human.
- The request is **documented before** the deletion, so there is a record even if the flow breaks mid-way.
- Every deletion writes an **audit record**: who requested, what was verified, timestamp, what was removed, which agent/call.
- The resident receives **clear instructions** (voice + a follow-up WhatsApp message with the app link) on how to enter new details.
- **Follow-up:** if new payment details are not entered within a defined window (e.g. 48–72h), the system flags the resident for staff follow-up.

**Verification method — to be defined with Homies.** Options: match on caller ID + apartment/building + ID number + a detail only the resident would know. Whatever is chosen must be strong enough to authorize deleting financial data.

> ⚠️ **This requires WRITE access to OXS.** OXS has no API, so deleting payment info means **RPA (Playwright) automation** logging into OXS as a user. This must be approved by Homies and, ideally, acknowledged by the OXS vendor. See §6 and §10.

> ⚠️ **Operational risk — no payment method gap.** Between deletion (step 4) and the resident re-entering details (step 5), the resident has **no active payment method**. If they never complete it, billing/direct debit silently stops and they become a debtor — creating the very problem Purpose 2 exists to solve. The follow-up flag above is a mitigation, not a cure. **Recommend reviewing this flow with Homies** — a safer variant is to collect new details first, or have staff confirm deletion, rather than deleting on the resident's word alone.

### 2.4 Payment Link
- Payment links are **generated by the OXS system** (not by us)
- The agent/bot **sends the OXS payment link** to the resident via WhatsApp
- Link send events are logged (who, when, which balance)

### 2.5 Customer Support — Complaint Tickets
- Agent captures complaints and opens a **ticket**
- Records: resident, building/unit, complaint category, description, timestamp, channel
- Sends a summary to the responsible team
- Escalates to a human immediately if the resident is angry, the issue is sensitive (safety/security/legal), or they ask for a person

## 2B. Purpose 2 — Outbound Debt Follow-Up (later phase)

⏸️ **Not in v1 scope.** Documented so the architecture supports it without rework.

The same voice agent, running outbound: calls residents with open debts, explains the balance, offers to send the OXS payment link, logs the outcome, retries no-answers, escalates disputes to a human, and produces a daily report.

**Design implications for v1 (build these in now):**
- The data model already includes debt and call-outcome fields
- The same tools (`send_payment_link`, `transfer_to_human`, `identify_resident`) are reused
- Telephony must support **outbound** calling with an Israeli caller ID, not just inbound
- Duplicate-prevention (last-contact date/outcome per debt) must exist before outbound starts

## 3. Channels

| Channel | Tech | Use |
|---|---|---|
| **Voice** | Vapi (Hebrew STT/TTS) + Telnyx number | Inbound service extension; resident calls in |
| **Chat** | WhatsApp (Meta Cloud API) + Chatwoot | Text conversations, payment links, handover to agents |

Both channels share the **same backend logic and data** — one brain, two front doors.

---

## 4. Human Handover (mandatory)

Every flow must offer a path to a person.

- **Voice:** warm transfer to a rep (AI whispers a summary first). If no rep is available → log a callback task and tell the resident.
- **WhatsApp:** staff takes over the conversation; the bot switches off for that thread.
- **Triggers:** explicit request for a human · anger/distress · payment disputes · safety or legal issues · agent cannot resolve

---

## 5. Capacity & Performance

**Volume target:** 50–80 residents/day expected · **system must handle 200/day**

Derived requirements (assuming an 8-hour service window):
- ~25 interactions/hour at peak load
- **Concurrent calls: support at least 10 simultaneous** (headroom for bursts)
- Queue/retry rather than reject when at capacity

**Performance targets:**
| Metric | Target |
|---|---|
| Voice response latency (voice-to-voice) | **< 800 ms** (currently 1500 ms — needs tuning) |
| WhatsApp bot first response | < 3 s |
| Successful resident identification | > 90% |
| Interactions resolved without a human | > 60% |
| Uptime | 99% during business hours |

## 6. Technical Architecture

```
Resident ──phone──▶ Telnyx ──▶ Vapi (Hebrew voice agent)
                                    │
Resident ──WhatsApp──▶ Chatwoot ────┤
                                    ▼
                              n8n  (brain: logic, tools, routing)
                                    │
                ┌───────────────────┼──────────────────┐
                ▼                   ▼                  ▼
           Supabase          Google Sheets /       Staff
        (all records)         OXS bridge         (tasks, handover)
```

**Components:**
| Layer | Tool |
|---|---|
| Voice agent | **Vapi** (Azure Hebrew STT + TTS, GPT-4.1-mini) |
| Telephony / number | **Telnyx** (+972 number, SIP) |
| Chat channel | **Meta WhatsApp Cloud API** |
| Agent inbox | **Chatwoot** (departments, assignment, bot on/off) |
| Automation brain | **n8n** (tools, logic, routing, reports) |
| Database | **Supabase** (residents, requests, tickets, calls, payments log) |
| OXS bridge | **Google Sheets** (batch) — Playwright/RPA only if live reads are required |
| Dashboard | **Next.js** internal web app |
| Hosting | **VPS** (n8n, Chatwoot) + **Vercel** (dashboard) + domain/Cloudflare |

## 7. Agent Tools (n8n endpoints)

| Tool | Purpose |
|---|---|
| `identify_resident` | Match caller/sender to unit + building |
| `verify_identity` | **Hard gate** before any destructive action (§2.3) |
| `open_request` | Create a new service request |
| `get_request_status` | Look up status of an existing request |
| `open_complaint_ticket` | Log a complaint ticket |
| `send_payment_link` | Send the OXS-generated payment link via WhatsApp |
| `log_payment_change_request` | Document the change request **before** any deletion |
| `delete_payment_info` | ⚠️ Truncate payment details in OXS via RPA — **requires verification to have passed** |
| `send_app_instructions` | WhatsApp the resident how to re-enter details in the OXS app |
| `transfer_to_human` | Warm transfer / assign to agent |
| `schedule_callback` | Log a callback when no human is available |

All tools are **channel-agnostic** — the same n8n webhooks serve both voice and chat.

**Guardrail:** `delete_payment_info` must reject any call where `verify_identity` has not succeeded for that interaction. Verification state is held server-side in n8n/Supabase — never trusted from the agent's own claim.

## 8. Data Model (core tables)

- `residents` — name, phone, unit, building, language
- `requests` — type, description, status, resident, unit, opened_via, oxs_ref
- `tickets` — complaint category, description, status, assigned_to
- `payment_events` — link sent, amount, channel, timestamp, status
- `payment_change_requests` — resident, requested_at, verification_result, deleted_at, re_entered_at, status, follow_up_flag
- `verification_attempts` — interaction, method, fields checked, passed/failed, timestamp
- `interactions` — channel, transcript/summary, disposition, duration
- `escalations` — reason, sensitivity flag, assigned_to, outcome
- `staff_users` / `departments` / `audit_log` — access control and traceability

---

## 9. Language & Tone

- **Hebrew-first.** Natural, calm, respectful, concise.
- Must not feel like "being thrown to a robot."
- Never aggressive or pressuring — especially on payment topics.
- ⚠️ **Constraint discovered:** Deepgram (the default STT) does **not** support Hebrew. Hebrew transcription must use **Azure, Gladia, ElevenLabs Scribe, or Speechmatics**.

---

## 10. Security & Compliance

- Role-based access; staff see only what their department needs
- Full audit log of every agent action and data access
- Resident financial data (balances, payment links) treated as sensitive
- Recording/transcript retention policy to be defined
- ⚠️ **Open:** call-recording consent requirements under Israeli law — must be confirmed before go-live
- Credentials stored in n8n credential store / env vars — never in code or chat

---

## 11. Success Criteria

1. Residents can open a request, check status, and get a payment link **without a human**
2. Complaint tickets are captured with complete, structured data
3. Handover to a human works reliably on both channels
4. System sustains **200 interactions/day** with < 800 ms voice latency
5. Measurable reduction in repetitive calls reaching staff
